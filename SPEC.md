# zap-sh Generation Specification

`SPEC-VERSION: 1`

This document is the **canonical contract** for what `zap-sh init` produces. It
exists so that a second implementation (the JavaScript generator in
`packages/generator/` and the browser wizard in `docs/`) can reproduce the exact
output of the bash `zap-sh` script.

## 0. Oracle principle

The bash `zap-sh` script is the **reference oracle**. For identical inputs, any
other implementation MUST produce **byte-for-byte identical** output. A shared,
language-agnostic conformance suite (`test/conformance/`) is run by both the bash
runner and the JS runner in CI so the two can never drift.

If the JS implementation and bash disagree, **bash wins** — unless the difference
is a genuine bash bug, in which case implementation STOPS and the discrepancy is
surfaced for a decision before either the code or this spec is changed.

This spec covers **generation only** — the `init` path (both CLI and wizard
collect the same variables and feed one generator). It does **not** cover
`update`, `snip`, `upgrade`, or any filesystem re-templating.

## 1. Inputs

Generation is a pure function of:

| Input | Source | Notes |
|-------|--------|-------|
| `template` | `-t <name>`, wizard prompt, or default | One of `basic`, `enhanced`. Default `basic`. |
| `project` | positional arg or wizard prompt | Validated `^[a-zA-Z0-9_-]+$`. Becomes the `app` variable. |
| `variables` | `--key=value` flags / wizard answers | `key` validated `^[a-zA-Z_][a-zA-Z0-9_]*$`. First occurrence wins. |
| `license` | `--license=<code>` or wizard | Optional. Code is matched case-insensitively against `templates/licenses/*.txt`. |
| `output_path` | `-o <path>` or `--output_path=` | Defaults to `<project>.sh`. Controls filename only, not content. |

The reference implementation reads `year` from the system clock
(`date +%Y`). This is the **only** non-deterministic input. See §6.

## 2. Templates

Templates live in `templates/`:

- `templates/basic.sh` — minimal template.
- `templates/enhanced.sh` — full-featured template.

The JS generator MUST consume these exact files (bundled at build time), never a
hand-copied duplicate. Licenses live in `templates/licenses/*.txt`.

Each template is a valid bash script partitioned into **sections** by markers
(§3). The template's own line-1 shebang is **not** part of any section and is
**not** copied to the output; the generator emits a fresh shebang (§5).

## 3. Section model

Sections are delimited by markers at the **start of a line**:

```
##( name        # opening marker for a major section
...content...
##) name        # closing marker
```

(Subsection markers `##[ name` / `##] name` exist inside sections but are
**not** used by generation — they are copied verbatim as ordinary content.)

**Extraction** (`extract_section`) is exactly:

```
sed -n '/^##( <name>$/,/^##) <name>$/p'
```

That is: every line from the **first** line equal to `##( <name>` through the
**first** subsequent line equal to `##) <name>`, **inclusive of both markers**.
The match is anchored (`^...$`) — the whole line must equal the marker (a single
space after `(`/`)`), so `##(name` or `## ( name` do not match.

The generated script is assembled from these sections, **in this fixed order**:

```
header  configuration  metadata  globals  helpers  app  core
```

(Source: `_SECTIONS` in `zap-sh`.) A section absent from a template is silently
skipped. Both shipped templates contain all seven.

The `header` and `app` sections carry user-owned / identity content; the
remaining sections are framework code. (Generation treats all seven identically;
the preserve/update split only matters for the `update` command, out of scope
here.)

## 4. Variables and substitution

### 4.1 Variable set

The generator assembles a variable map from **user variables** (CLI flags /
wizard answers) and **computed defaults**. The defaults:

| Variable | Default value | Condition |
|----------|---------------|-----------|
| `app` | `<project>` | always |
| `year` | `<current year>` (`date +%Y`) | always (see §6) |
| `detail` | `Generated by zap-sh` | always |
| `description` | `Generated by zap-sh template` | always |
| `author` | `anonymous` | only if user did not supply `author` |
| `version` | `0.1.0` | only if user did not supply `version` |
| `email` | `` (empty string) | only if user did not supply `email` |
| `license_name` | `MIT License` (fallback) or `<Basename> License` | always (see §7) |
| `license_content` | `` or substituted license text | only when non-empty (see §7) |

Placeholders actually referenced by the shipped templates:
`app`, `detail`, `description`, `author`, `email`, `version`, `year`,
`license_name` (basic + enhanced), `license_content` (**enhanced only**).

### 4.2 Substitution rules

- A placeholder is the literal text `{{name}}`.
- Substitution replaces **every** occurrence of `{{name}}` with the value,
  globally, across the section content.
- Values are substituted literally — an empty value yields an empty string
  (e.g. empty `email` renders `# AUTHOR: anonymous <>`).
- Substitution is applied section-by-section after extraction, then the result
  is terminated with a single newline (§5).

### 4.3 Precedence (user wins)

The merged list is `user_variables ++ default_variables`, processed in order.
Because each placeholder is fully consumed by the **first** variable whose name
matches, a user-supplied `author=…` is applied before the default `author=…`
default and therefore wins. Rule: **for any variable name, the user value takes
precedence over the computed default.** For a given name, only the **first**
`key=value` among the user variables is used (later duplicates are dead once the
placeholder is gone).

**Sequential, whole-buffer substitution.** Each variable's pass replaces its
placeholder across the *entire current buffer*, including text introduced by an
earlier variable's value. Consequently a placeholder token that first appears
*because* an earlier variable's value contained it **is** substituted — but only
by a variable processed **later** in the sequence, never by one already applied.
Worked example (basic template, `--year=2025`, no author):

- `detail="has {{version}} literal"` → the `{{version}}` token, introduced when
  `detail` is applied, is later replaced by the default `version=0.1.0`
  (processed after `detail`) → `has 0.1.0 literal`.
- `description="has {{author}} literal"` → `{{author}}` is later replaced by the
  default `author=anonymous` → `has anonymous literal`.

The order is therefore load-bearing: user variables first (in the order given),
then the defaults in the fixed sequence `app, year, detail, description,
author, version, email, license_name, license_content`. `license_content` is a
special case: it is produced by a **prior** substitution pass over the license
file (§7) — using the full variable map — before it enters the main pass as a
value.

## 5. Output assembly

1. The output file begins with exactly:

   ```
   #!/usr/bin/env bash
   ```

   followed by a newline.
2. For each section in the §3 order that exists in the template: extract it
   (§3), substitute variables (§4), and append the result followed by a single
   `\n`.
3. The resulting file therefore ends with exactly one trailing newline.
4. The output file is made executable (`chmod +x`; mode `0755` modulo umask).
5. The output filename is `output_path` if provided, else `<project>.sh`. Parent
   directories are created if necessary. Filename does not affect file content.

Command substitution semantics (bash `$(...)`) strip trailing newlines from each
extracted section before the single `\n` terminator is re-added, so blank lines
*inside* a section are preserved but no section contributes more than one
trailing blank line.

## 6. Determinism

`year` is the only clock-derived input (`date +%Y`). For reproducible output
(and for the conformance suite), `year` MUST be pinnable:

- Bash: pass `--year=<YYYY>` (a user variable, so it is applied before the
  default `year=$(date +%Y)`).
- JS: `generate()` accepts an explicit `year`; it MUST NOT read the system clock
  implicitly when `year` is provided.

**Precise scope of `--year`.** The default `year=$(date +%Y)` is *always* part of
the variable map, appended after the user variables. Because substitution is
sequential (§4.3), the pinned user `year` wins for every `{{year}}` token that is
present in the template or license text at the start of the pass (this is all
real occurrences — the enhanced header's `Copyright (C) {{year}}` and the license
files' `{{year}}`). The **only** residual clock dependence is the pathological
case where a *user-supplied value* itself contains the literal token `{{year}}`:
that token is introduced after the user `year` pass has run, so it is caught by
the later default `year` (the clock value), not the pinned one. Conformance
fixtures therefore never embed `{{year}}` inside a field value; the ordering rule
is instead locked with `{{version}}`/`{{author}}` (see the
`basic-placeholder-literal` fixture).

Apart from `year`, no generation input depends on ambient state (locale,
timezone, environment) for the produced bytes.

## 7. Licenses

License files are `templates/licenses/*.txt`. Discovery and naming:

- **Available codes** = basenames of `*.txt`, **lowercased**, **sorted**
  (`apache`, `gpl`, `mit`). The wizard's default license is the **first** of this
  sorted list (`apache`).
- A user license code is resolved case-insensitively to a file
  (`find -iname "<code>.txt"`).
- **`license_name`**:
  - If a license is selected and the file is found: `"<Basename> License"`,
    where `<Basename>` preserves the file's actual case
    (`MIT.txt` → `MIT License`, `Apache.txt` → `Apache License`,
    `GPL.txt` → `GPL License`).
  - If **no** license is selected: the fallback is `"MIT License"` with **empty**
    `license_content`. (Note the asymmetry: the no-license fallback *name* is
    `MIT License` even though the wizard's default *selection* is `apache`.)
- **`license_content`**:
  - When a license is selected: the license file's text, run through the **same
    substitution engine** (§4.2) with the full variable map, so the license's own
    `{{year}}`/`{{author}}` placeholders are resolved.
  - When no license is selected: empty string.
  - `license_content` is only referenced by the **enhanced** template header; in
    the **basic** template the placeholder does not appear, so a selected
    license affects only `license_name` there.

## 8. Validation and errors (generation-relevant)

- Project name must match `^[a-zA-Z0-9_-]+$`; else usage error.
- `--key` names must match `^[a-zA-Z_][a-zA-Z0-9_]*$`; else usage error.
- Template must be one of `basic`, `enhanced`; else usage error.
- A selected license code with no matching file is an error.

These govern acceptance/rejection of inputs; when inputs are valid the produced
bytes follow §1–§7.

## 9. Version stamp

This spec is versioned by `SPEC-VERSION` at the top. Any change to observable
generation behavior requires a `SPEC-VERSION` bump and a corresponding update to
the conformance fixtures. The bundled template `__ID__` (e.g. `basic-1.0.0`) is
part of template content and travels with the template files, not with this spec.

## Appendix A — Worked example (observed output)

`zap-sh init demo-basic -t basic --year=2025` (no license, empty email) produces
a header beginning:

```
#!/usr/bin/env bash
##( header
# --------------------------------------------------------------------
# demo-basic - Generated by zap-sh
#
# Generated by zap-sh template
# --------------------------------------------------------------------
# AUTHOR: anonymous <>
# VERSION: 0.1.0
# LICENSE: MIT License
# --------------------------------------------------------------------
# __TEMPLATE__: https://github.com/budhash/zap-sh/blob/main/templates/basic.sh
# __ID__: basic-1.0.0
# --------------------------------------------------------------------
##) header
```

`zap-sh init demo-enh -t enhanced --year=2025 --author=Bob --license=apache`
embeds the Apache text (with `{{year}}`/`{{author}}` resolved) into the enhanced
header via `{{license_content}}`, and sets `LICENSE: Apache License` via
`{{license_name}}`.
